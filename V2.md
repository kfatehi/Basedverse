# Visit 2.0: one file

Ticket: [#22](https://github.com/sarmiena/Basedverse/issues/22). Branch: `visit-2`. Nothing of it reaches `main`
until all of it is built and proven (section 9); then one pull request, and release 2.0.0.

## 1. What it is

**The one `visit` program is the whole of basedverse that a workroom needs.** Today a workroom needs
visit-client, auth-client, Postgres (in Docker, or one of its own) and visit-engine (a Docker image with
Chromium). In 2.0 it needs one file per platform, with everything inside it:

- visit-client, auth-client and the engine's driver, as one Rust program;
- Postgres;
- a headless Chrome for the engine;
- every library and font those two need, so nothing is asked of the machine but its operating system.

Nothing is downloaded when it runs, nothing is installed, no Docker. The rest of basedverse a person uses is
documentation: how to integrate Visit into a room, for their LLM to implement.

Docker stays where it is useful to us: building, testing, CI. Never in what someone runs.

Platforms, as today: Linux x86_64 and arm64 (any distribution with glibc 2.28 or newer: Debian 10+, Ubuntu
20.04+, RHEL 8+), macOS Apple silicon and Intel, Windows x86_64.

## 2. The program

One binary, `visit`, from a Cargo workspace at the repository's root:

| crate | where | what |
|---|---|---|
| `visit` | `visit/client/` | the binary: the page server, the lobby, links, the database's lifecycle, the commands |
| `auth` | `auth/client/` | a library: accounts, sessions, keys, the sign-in API |
| `engine` | `engine/` | a library: drives the headless Chrome that hosts the room's server page |

### 2.1 Commands

| command | does |
|---|---|
| `visit` | runs the workroom's Visit: Postgres, the sign-in API, the page server, the lobby and links, and the engine when the room has a server page (`ENGINE_ROOM_URL`). One process; Ctrl-C (or SIGTERM) stops all of it, Postgres last |
| `visit auth user add <name>` | as `auth-client user add` today; likewise `auth user list`, `auth user remove`, `auth passwd`, `auth sessions`, `auth revoke`, `auth key add|list|revoke` |
| `visit import <postgres URL>` | moves a 1.x workroom's database in (6.3) |
| `visit psql` | a `psql` on the workroom's database, as its superuser |
| `visit status` | where its data is, the versions inside it, whether it runs |
| `visit --version` | its version, and the Postgres and Chrome inside it |

`visit-client migrate` and `auth-client migrate [--admin]` are gone: `visit` brings its database up to date
itself, every start. A command that needs the database while `visit` runs uses the running one; otherwise it
starts Postgres for itself, does its work and stops it.

### 2.2 Settings

Every setting keeps the name it has today, so a launcher's `.env` mostly carries over. A flag for each, a flag
wins over its variable, as today.

| variable | default | |
|---|---|---|
| `VISIT_DATA_DIR` | `<the user's data folder>/basedverse/<the workroom's name>` | everything it keeps (3). `bin/setup` writes it into the `.env` once, so a renamed workroom keeps its data |
| `VISIT_LOBBY`, `VISIT_NAME`, `VISIT_SIM`, `VISIT_PORT`, `VISIT_LISTEN`, `VISIT_TOKEN_FILE`, `VISIT_USER_TOKEN_FILE`, `VISIT_MAX_VISITORS`, `VISIT_IDLE_EXIT`, `VISIT_RELAYS`, `VISIT_ORIGINS` | as today | visit-client's |
| `VISIT_STATE_FILE`, `VISIT_CACHE_DIR` | in `VISIT_DATA_DIR` | as today |
| `AUTH_PORT`, `AUTH_LISTEN`, `AUTH_TOKEN_FILE`, `AUTH_IDLE`, `AUTH_MAX_AGE` | as today | the sign-in API's (flags `--auth-port`, …) |
| `ENGINE_ROOM_URL` | none: no engine | the room's server page (`http://127.0.0.1:3001/room/server`) |
| `ENGINE_PORT`, `ENGINE_TICK_IDLE`, `ENGINE_MEMORY_MAX`, `ENGINE_WINDOW`, `ENGINE_LOG`, `ENGINE_DEBUG` | as today | the engine's (flags `--engine-port`, …) |

Gone: `VISIT_DATABASE_URL`, `AUTH_DATABASE_URL`, `VISIT_DATABASE_ADMIN_URL`, `VISIT_DATABASE_NEW_ADMIN_URL`,
`AUTH_VISIT_PROBE`, and the engine's `ENGINE_KEY_FILE`, `VISIT_HOST` and its `VISIT_TOKEN_FILE`: they joined two
programs that are one now. There is no setting for a Postgres of one's own: the one inside is the database.

## 3. What it keeps

`VISIT_DATA_DIR` (the user's data folder: `$XDG_DATA_HOME` or `~/.local/share` on Linux, `~/Library/Application
Support` on macOS, `%LOCALAPPDATA%` on Windows):

```
<VISIT_DATA_DIR>/
  state.json            visit-client's state file (VISIT_STATE_FILE)
  landscapes/           friends' landscapes (VISIT_CACHE_DIR)
  postgres/data/        the database
  postgres/secrets      its roles' passwords (the superuser, visit, auth), readable by the user only
  postgres/log          Postgres' own log
  engine/profile/       the headless Chrome's profile, made new each start
```

The programs inside `visit` are unpacked once into `<the user's data folder>/basedverse/runtime/`, a directory
per version (`postgres-18.6-1/`, `chrome-156.0.8078.73-1/`), shared by every workroom of that user, checked
against the sha256 they were built with before each start, and unpacked again if anything is off. A version no
`visit` uses any more is removed by the next start of one that doesn't.

## 4. The database

Postgres, run by `visit` as a child process through
[`postgresql_embedded`](https://github.com/theseus-rs/postgresql-embedded) (no features: it never downloads;
`trust_installation_dir` on the unpacked runtime).

- **First start:** `initdb` into `postgres/data` with the built-in `C.UTF-8` locale (the same on every
  platform), SCRAM passwords, the superuser's password generated into `postgres/secrets`.
- **Every start:** Postgres on `127.0.0.1`, on a port free at that moment (nothing outside `visit` needs it;
  `visit psql` and the commands read it from `postmaster.pid`). Then, as the superuser: the roles `visit` and
  `auth`, each plain, with its own schema and a generated password (auth's role code of 0.21, `migrate
  --admin`); then each schema brought up to date (both migration sets, as today), each as its own role. A
  Postgres left running by a `visit` that was killed is stopped first.
- **Stop:** Postgres stops after everything else (a fast shutdown).
- Nothing about the schema, the roles, LISTEN/NOTIFY or the advisory locks changes: the code that talks to the
  database is today's.

### 4.1 Upgrading Postgres

A new minor version (18.6 to 18.7) is a new runtime directory and the same data. A new major version (18 to
19) needs `pg_upgrade` with both runtimes: not in 2.0; the archive keeps `pg_upgrade` for it.

## 5. The engine

engine/driver/engine.py, in Rust (`engine` crate), doing everything engine/SPEC.md section 5.1 says (the page,
its key, the shim, drawing free, visible and focused, ticking, reloads with backoff, the memory ceiling,
`/health`, `ENGINE_DEBUG`'s `/debug/eval` and `/debug/crash`), with these differences:

- **The Chrome is the one inside `visit`:** Chrome for Testing's `chrome-headless-shell` at a pinned version,
  never the machine's own Chrome. Chrome's own sandbox (no container to stand in for it now).
- **Spoken to over the devtools protocol on `127.0.0.1`**, its port picked by Chrome (`--remote-debugging-port=0`,
  read back from `DevToolsActivePort`), the same on every platform.
- **In-process:** the host token and visit-client's port are handed over directly; the key the room's server
  takes from the engine is made by `visit` itself at each start (an API key labelled `engine`, made new each
  start, the old one revoked), so there is no key file and no `auth key add engine` step.
- **Memory:** the browser's processes' proportional set size where the platform has one (Linux), their resident
  size elsewhere.
- `shim.js` is unchanged, built into the program.

The engine runs when `ENGINE_ROOM_URL` is set, as before for a room with a server half (engine/SPEC.md 8).

## 6. Around it

### 6.1 The dependencies: `deps/`

How the Postgres and the Chrome inside `visit` are made, kept in this repository for every upgrade
(deps/README.md):

| | Postgres | Chrome |
|---|---|---|
| Linux | compiled from source in manylinux_2_28 (glibc 2.28), only the C library under it | Chrome for Testing's headless shell, with the libraries it needs and a font packed beside it, taken from the same base |
| macOS | compiled from source on the runner, relocatable | Chrome for Testing's headless shell |
| Windows | theseus-rs/postgresql-binaries' build, checked and cut down | Chrome for Testing's headless shell |

- `deps/versions.env`: the versions, our build number, every input's sha256, build images by digest.
- `deps/<postgres|chrome>/build <platform>` makes the archive and tests it (`deps/<…>/test`: Linux ones on bare
  Ubuntu 20.04 and Debian 12, the others natively). The `deps` workflow runs both on every platform on each push
  that changes `deps/`, and **publishes** on a tag `deps-<n>` (the release `deps-<n>`, never marked latest).
- `deps/pin` writes `deps/pinned.json`: each archive's URL and sha256, per platform.

Upgrading Postgres or Chrome: bump `versions.env`, push (CI builds and tests it everywhere), tag `deps-<n+1>`,
`deps/pin`, commit. Visit's own releases don't change.

### 6.2 Building `visit`

The `visit` crate's `build.rs` takes the pinned archives for the platform it builds for (`deps/pinned.json`,
downloaded once into a cache and checked against their sha256, or from `VISIT_DEPS_DIR` when set: what
`deps/<…>/build` made locally), and builds them in. `release.yml` builds and tests `visit` on each platform and
then **starts it fresh there**: Postgres up, a user made and signed in through the API, a room page hosted by the
engine, stopped. The release assets are `visit-<target>` (`.tar.gz`, `.zip` on Windows) and `SHA256SUMS`.

### 6.3 Moving a 1.x workroom over

`visit import <URL of the old database, as its superuser>` copies the `visit` and `auth` schemas (chat, media,
held whispers, bans, accounts, sessions, keys) into the new database with the `pg_dump` and `pg_restore` inside
`visit`, once, into a database with nothing in it yet. Then the old `visit-db` container (or Postgres) can go.

The CHANGELOG's 2.0.0 entry has "Upgrading" for a launcher: one `visit` in place of four services, the settings
that went, `visit import`, the engine's key step gone.

### 6.4 `bin/setup`

Downloads `visit` for the machine (or builds it), sets `VISIT_DATA_DIR`, writes the tokens, makes the owner's
account (`visit auth user add`). No question about a database or Docker.

### 6.5 The documentation

visit/, auth/ and engine/ SPEC.md and INTEGRATING.md, the READMEs, the plugin's VISIT.md guidance and the
CHANGELOG, written for 2.0: one program, how a launcher runs it, how a room's server reaches it. A greenfield room
built from them alone comes out right.

### 6.6 Tests

- Unit tests per crate, as today.
- The end-to-end tests (`run-e2e.sh`, auth's) and the browser test run `visit` as built, its own Postgres and
  engine inside: no Postgres container, no engine image. They still run in Docker on our machines and CI.
- `release.yml`'s fresh start on every platform (6.2) is the proof that it is portable.

## 7. The Sweatshop

The first workroom moved over: its compose's `visit-db`, `auth`, `visit` and `engine` services become one
`visit`, its database imported (6.3). Run at the desk, then from the laptop, as 1.0 was proven.
